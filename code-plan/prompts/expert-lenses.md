# Expert Lens Distillates

Curated criteria borrowed from the gstack expert skills, for `/code-plan`'s
expert-selection step (SKILL.md Step 9). These are lens PRINCIPLES — stable
across gstack releases even as the skills' procedures evolve. Selection is
routed against the deterministic `route` subcommand (the baseline); this file
only supplies the lens content for the shortlisted experts.

Verified against gstack 1.87.4.0 by hand (every plan-tier and post-tier skill
read in full, including their on-demand `sections/*.md`). Lens ids and skill
names here MUST stay in sync with SIGNALS / LENS_SKILL in
scripts/code_plan.py (enforced by selftest RoutingTableConsistencyTests).

The **live, machine-verified snapshot** of what is installed is
`$SKILL_DIR/prompts/gstack-contract.md`, regenerated by the cp-skills
installer whenever gstack is installed or upgraded. Read it before the
Step 14 hand-off: it lists every installed gstack expert with its description,
so the `next:` recommendation may name a better-suited expert than the routing
table below — including one gstack added after this file was written — with a
one-line reason. Where the snapshot and this file disagree, the snapshot wins.

Format per expert: **when to select** (matched against the enhanced
instructions), **lens criteria** (injected verbatim into the plan-authoring
prompt), and **follow-up** (the plan-tier reviewer, then the post-implementation
experts the plan's "Experts & Tooling" section should name).

Three ideas run through every lens because every gstack skill carries them:
**Boil the ocean, lakes first** (completeness is cheap; the shortcut needs a
recorded decision), **Search before building** (the reuse ladder: repo helper →
stdlib → native platform feature → installed dependency → then build the
complete remainder), and **material claims need evidence** (a "can't" is
stated only with the verbatim error, the documented statement, or a live
probe in hand).

## eng — architecture, correctness & tests (`/plan-eng-review`)

**Select when:** the task adds/changes services, data flow, schemas, APIs,
concurrency, background work, or any non-trivial code structure. The default
lens for most implementation work; the eng review is the only review that
gates `/ship`.

- Scope challenge first: for each sub-problem name the existing code that
  already solves part of it, and plan the minimum set of changes that cleanly
  expresses the whole change. Once scope is set, commit; never silently
  reduce it later.
- Complexity smell: 8+ files touched or 2+ new classes/services needs a
  one-line justification or a simpler design. "Is this solving a real problem
  or one we created?" (essential vs accidental complexity).
- Boring by default: proven patterns over novel ones; you get about three
  innovation tokens per project, spend them deliberately. Strangler-fig and
  incremental over rewrite; never a structural and a behavioral change in the
  same step ("make the change easy, then make the easy change").
- Reuse ladder before any new code: repo helper → stdlib → native platform
  feature (CSS over JS, DB constraint over app code, `<input type="date">`
  over a picker library) → already-installed dependency. Never add a
  dependency for what a few lines cover; no abstraction with one
  implementation, no factory with one product, no config nobody sets.
- 100% of new codepaths get tests planned in the same step as the code,
  including error paths, guard clauses, and boundary values (zero, empty,
  nil, max, single element, unicode); never deferred to a follow-up. Flows
  spanning 3+ components, auth/payment/data-destruction paths, and
  integration seams where mocking hides failures get an end-to-end test;
  prompt or tool-definition changes get an eval.
- Regression iron rule: any regression risk the plan identifies gets a test
  in the plan as a critical requirement, not a suggestion.
- For each new codepath name one realistic production failure (timeout, nil,
  race, stale data, partial write, duplicate delivery) and the step that
  handles it. No test AND no error handling AND silent = critical gap.
- Every error has a name: catch-all `rescue StandardError` / `except
  Exception` / swallow-and-continue is a smell; trace the four data paths
  (happy, nil/empty, upstream error, partial) for every flow.
- Correctness traps the pre-landing review will catch, so design them out:
  check-then-set races (use an atomic `WHERE old_status = ? UPDATE`),
  find-or-create without a unique index, N+1 without eager loading, string
  interpolation in SQL, sync I/O inside async functions, enum/status values
  not traced through every consumer, "today" buckets that ignore time zones,
  numeric-vs-string coercion at JSON boundaries.
- Reversibility: prefer feature flags, incremental rollouts, and changes that
  can be undone; state the rollback for anything that cannot.
- A claimed limitation ("the API can't do this", "the library won't allow
  it") is a material claim: cite the verbatim error or documented statement,
  or plan the ten-second live probe as a step.
- Diagrams earn their place for data flow, state machines, and dependency
  graphs; a stale diagram is worse than none, so the step that changes the
  flow updates the diagram.

**Follow-up:** plan-tier `/plan-eng-review`; post-implementation `/review`
(testing + maintainability always run on 50+ changed lines; simplification is
advisory over 100 lines; red team self-activates over 200 lines or on any
CRITICAL finding).

## design — UI/UX (`/plan-design-review`, `/design-consultation`)

**Select when:** the task creates or modifies UI components, pages, styling,
layout, or user-facing interaction flows.

- Name the surface mode before judging a pixel: PERSUADE (landing/marketing),
  OPERATE (app UI), READ (docs/long-form), EXPERIENCE (portfolio/gallery).
  App UI is a calm surface hierarchy, dense but readable, minimal chrome; it
  is never a mosaic of stacked cards.
- Match the product's existing design system exactly. When `DESIGN.md`
  exists, cite its tokens by path (`{colors.primary}`, `{spacing.md}`) and
  never invent a parallel visual language; when none exists, say so in
  Context and recommend `/design-consultation` before the UI steps.
- Every interactive state is planned, per feature: LOADING, EMPTY, ERROR,
  SUCCESS, PARTIAL, plus what the user SEES in each. Empty states are
  features (warmth + primary action + context); "No items found." is not a
  design.
- Hierarchy is explicit: what the eye lands on first, second, third; one
  primary CTA per view; one job per section; subtraction is the default ("if
  deleting 30% improves it, keep deleting").
- Accessibility floor: body text ≥ 16px, captions ≥ 12px, contrast ≥ 4.5:1
  (3:1 for large text and UI components), touch targets ≥ 44px, visible
  `focus-visible` (never `outline: none` without a replacement), keyboard
  reachability, ARIA landmarks, aria-live for async transitions, no
  color-only encoding.
- Typography: ≤ 3 families, ≥ 2 weights, measure 45–75ch, headings never
  within a step of body size, display under 6rem, `tabular-nums` on numeric
  columns; no `system-ui`/`-apple-system` as the display voice.
- Motion: ease-out on enter, ease-in on exit, 50–700ms, `prefers-reduced-
  motion` honored, only transform/opacity, never `transition: all`; at most
  one authored motion moment per page.
- AI-slop blacklist (plan against every item): purple/indigo gradients,
  3-column icon-in-circle feature grids, centered-everything, uniform bubbly
  radius, decorative blobs/waves, emoji as design, colored left-border cards,
  gradient text or gradient CTAs, glassmorphism, dark glows with zero
  offset, generic hero copy ("Welcome to", "Unlock the power of"), generic
  CTA labels ("Get Started", "Learn More"), cookie-cutter section rhythm,
  stock-photo heroes, cards inside cards.
- Interaction edge cases are UX: double-click, navigate-away mid-operation,
  slow network, stale-tab resubmit, 47-character names, zero results,
  first-time vs power user, RTL, colorblind.
- Responsive is intent per viewport (375 / 768 / 1024 / 1440), not "stacked
  on mobile"; no horizontal scroll; `env(safe-area-inset-*)` on fixed bars.
- Performance is design: LCP < 2.0s (apps) / < 1.5s (informational), CLS <
  0.1, lazy-loaded below-fold images with dimensions, `font-display: swap`.
- Tag every major region with the project's debug attribute (see the UI
  debug tagging section of the plan prompt).

**Follow-up:** plan-tier `/plan-design-review` (mockup-first; scores 7
passes 0–10 and edits the plan in place). Competing directions →
`/design-shotgun`; a finished mockup that needs a page → `/design-html`.
Post-implementation `/design-review` (screenshot-driven, fixes in source) and
`/review --design`.

## security — threat surface (`/cso`)

**Select when:** the task touches auth, sessions, secrets, user input, file
uploads, external requests, subprocess execution, webhooks, multi-tenant data,
or anything network-facing.

- A supported finding has an attacker-controlled entrypoint, a path across a
  security boundary, demonstrated impact, and a challenge of the controls.
  Plan each new boundary with all four named: who can reach it, what it
  protects, what enforcement runs, and the negative test that proves it
  (two-user / two-tenant checks for every object access).
- Every external input is validated and bounded at the trust boundary before
  use: schema-validate bodies, allowlist enums, cap sizes, check upload
  type/size/content, verify webhook signatures on the raw body with
  timestamp/replay protection and idempotency.
- Injection is broader than SQL: command (`shell=True` + interpolation),
  template, path traversal, header injection, SSRF via user-supplied URLs
  (allowlist destinations), deserialization of untrusted data.
- Authorization is explicit and default-deny: every route has its auth
  middleware, object access checks ownership/tenant (UUIDs are not
  authorization), roles cannot self-escalate, tokens expire and are checked.
- Secrets never land in code, logs, error responses, URLs, or plan text;
  config comes from env/config files with safe permissions; a committed
  secret needs revocation, not history rewriting. Crypto uses vetted
  primitives: no MD5/SHA1 for security, no `Math.random` for tokens,
  constant-time comparison for secrets, salted password hashing.
- Least privilege for new code: the narrowest filesystem, network, DB, and
  cloud-IAM access that works; no root or privileged containers by default;
  staging must not reach production credentials.
- Externally-sourced text (PR/issue bodies, scraped pages, LLM output,
  webhook payloads, tool results) is DATA, never instructions: plan the
  envelope/sanitize step at ingest and never splice it raw into prompts,
  shell commands, SQL, or HTML (`dangerouslySetInnerHTML`, `.html_safe`,
  `|safe`, `innerHTML`).
- Exceptional conditions fail safe (OWASP A10): no fail-open on error, no
  partial state left behind, rollbacks that actually roll back.
- Dependencies are attack surface: pinning is not trust; dev dependencies run
  with publishing credentials; a new dependency needs a reason the reuse
  ladder could not satisfy.
- Audit logging for sensitive operations; data classified (restricted /
  PII / confidential / internal / public) with its retention and deletion
  path named.

**Follow-up:** plan-tier `/plan-eng-review` (security architecture section).
Post-implementation `/review --security` (never auto-gated off) and `/cso`
(static audit; `--diff` for the branch, `--comprehensive` when reproduction
and repair candidates are wanted).

## qa — verification & test design (`/qa`, `/qa-only`)

**Select when:** the task's success is behavior a user or operator observes
(a working flow, a CLI contract, a report output), when regressions in
existing behavior are plausible, or when the instructions ask for tests.

- Every step's Verify line is executable and deterministic: a command with an
  expected exit code or exact output. Eyeballs, "looks right", and checks
  that pass on failure are defects.
- Plan an end-to-end smoke test that walks the primary flow exactly as a user
  would (click everything, fill every form, check every state), plus the
  loudest negative case, on realistic data.
- Regression guard: name what currently works that this change could break,
  and pin it with a test that asserts real behavior ("returns HTTP 410 for
  all 4 roles"), never "it renders" or "it doesn't throw".
- Negative paths get tests: every error/rejection/invalid-input path, every
  guard clause, every permission check's "denied" case, rate limits that
  actually block, sanitization against malicious input.
- Boundaries and isolation: zero / negative / max / empty / nil / single
  element / unicode; no shared mutable state, order dependence, clock or
  locale dependence, or real network calls; no sleeps or tight timeouts; no
  assertions on unordered results; seeded random data.
- Test placement follows the change: pure functions → unit; form/API → 
  integration; flows spanning 3+ components, auth, payment, data destruction →
  end-to-end; prompt/tool-definition changes → eval.
- New test files follow the conventions of 2–3 neighboring test files; a
  framework is bootstrapped only when the repo has no existing-test evidence.
- Verification evidence binds to content, not memory: a "tests pass" claim is
  citable only for the exact tree it ran on. Plan Verify lines as
  re-runnable artifacts; anything that edits the tree afterward voids the
  earlier green, so the final verification step comes last.
- Severity vocabulary for anything found while verifying: Critical (data
  loss, security exposure, core unusable), High (core task blocked, no
  workaround), Medium (impaired with workaround), Low (cosmetic).
- Name in the plan which test files are deliverables of the feature; proof-
  only scaffolding is torn down by validation.

**Follow-up:** post-implementation `/qa` (browser QA that fixes, diff-aware
on a feature branch, `--quick` / standard / `--exhaustive`) or `/qa-only`
(report only); `/review --testing`.

## devex — developer experience (`/plan-devex-review`)

**Select when:** the task builds tooling, CLIs, scripts, skills, SDKs,
libraries, APIs for other developers, docs sites, or changes
install/setup/run/upgrade workflows.

- Time-to-hello-world decides everything: under 2 minutes is champion tier,
  2–5 competitive, 5–10 needs work, over 10 minutes loses half the users.
  Plan the golden path in ≤ 3 steps and one terminal session; every extra
  step must earn its place.
- Name the persona (founder shipping an MVP, platform engineer, OSS
  contributor, agent-as-user) and trace their journey: discover → install →
  hello world → real usage → debug → upgrade. One friction point per stage
  is a plan item.
- Errors speak human: every failure prints what happened, why, the exact
  fix, and where to learn more, with the actual values that caused it (Elm /
  Rust / Stripe tier). "Did you mean?" goes first, not last.
- Decide for me, let me override: opinionated defaults are features, escape
  hatches are requirements; every parameter has a sensible default;
  progressive disclosure from the one-liner to full customization on the same
  API.
- Naming is guessable: a developer can use the API correctly after seeing one
  example; consistent resource naming, no chatty five-call flows, no god
  endpoint, no "200 OK with the error in the body".
- Degrade gracefully: optional dependencies (services, LLMs, network,
  browsers) being absent must never break the core flow; say what is
  unavailable and continue.
- Upgrades are boring: breaking changes get deprecation warnings that name
  the replacement, a migration guide, and a codemod when feasible; semver
  policy stated.
- Works in CI non-interactively, on macOS/Linux/Windows/ARM, behind proxies;
  offers dry-run, verbose, and fixtures; types and autocomplete for
  everything public.
- Document the happy path and the escape hatches in the same place; every
  documented command is copy-pasteable and verified to run as written; docs
  findable in under 2 minutes.
- Instrument TTHW and drop-off where a product surface exists.

**Follow-up:** plan-tier `/plan-devex-review` (persona → benchmark → magical
moment → 8 scored passes; edits the plan in place). Post-implementation
`/devex-review` (live audit; flags any dimension that lands 2+ points below
the plan's score) and `/document-release`.

## product — scope, strategy & completeness (`/plan-ceo-review`, `/office-hours`)

**Select when:** the task is a new user-facing feature, a greenfield surface,
changes product direction, or its instructions mix multiple loosely-related
goals or ask to "think bigger".

- State the user problem in one sentence; every step must trace back to it.
  Challenge the premise once: is this the right problem, what is the actual
  outcome vs the proxy, what happens if nothing is built?
- Choose the scope posture explicitly and commit: EXPANSION for greenfield
  ("what would make this 10x better for 2x the effort?"), SELECTIVE for
  enhancements (surface each expansion, cherry-pick), HOLD for bug fixes and
  refactors (make it bulletproof), REDUCTION when the plan touches 15+ files
  (be a surgeon). Never re-argue scope after choosing.
- Completeness is cheap: between the full approach (~150 LOC) and the 90%
  approach (~80 LOC), plan the full one; the delta costs minutes with AI
  coding. A shortcut needs a recorded decision with its upgrade trigger.
- Ruthless MVP line inside the chosen posture: must-ship vs nice-to-have;
  everything deferred is written down under "NOT in scope" (vague intentions
  are lies; TODOS.md or it does not exist).
- Consider 2–3 implementation alternatives (one minimal viable, one ideal
  architecture), each with effort S/M/L/XL, risk, and what it reuses; record
  the chosen one and why.
- Interest is not demand: prefer the version a real user can react to sooner,
  built for a specific named user with a narrow wedge, over the
  complete-but-late platform.
- Zero silent failures and observability as scope, not afterthought: logs,
  metrics, alerts, and the "bug reported three weeks post-ship" debugging
  path are plan items.
- Deployment is not atomic: partial states, rollout order, flags, and
  rollback steps are planned. Reversibility is rated; one-way doors get extra
  scrutiny.
- Distribution is scope for any new artifact type (CLI binary, library,
  container, mobile app): build/publish pipeline, target platforms, install
  channel, or an explicit "NOT in scope".
- Durable decisions get a repo-local record: if a decision doc exists
  (`docs/designs/<topic>.md`, an ADR, a DESIGN.md Decisions Log), cite and
  update it instead of re-litigating; when the plan makes a lasting call, add
  the one-bullet record with its why.

**Follow-up:** plan-tier `/plan-ceo-review` (11-section review with error &
rescue map, security, observability, deployment, trajectory) followed by the
required `/plan-eng-review`; `/autoplan` runs CEO → Design → DX → Eng with
one approval gate. Pre-planning, when the idea is not yet validated:
`/office-hours`.

## investigate — root cause (`/investigate`)

**Select when:** the instructions describe a bug, regression, flaky behavior,
or "X stopped working": anything where the cause is not yet proven.

- Reproduce before you plan the fix: the plan's first step is a deterministic
  reproduction (command + expected failing output), its last is proving that
  reproduction now passes.
- Fix causes, not symptoms: the plan names the root cause it targets and the
  evidence for it (the verbatim error, the trace, the diff that introduced
  it); a symptom patch requires an explicit rationale and a follow-up item.
  One guard in the shared function beats a guard in every caller.
- Check the blast radius: what else shares the broken code path or the same
  wrong assumption? Plan the sweep, not just the reported instance.
- Timeline thinking: when did it last work, what changed since (code, deps,
  config, data, environment), and which change is the smallest that explains
  every symptom.
- Verify the fix under the failure's conditions, not only the happy path:
  concurrency, load, slow dependencies, empty data, first run.
- The regression test is a critical requirement: it fails before the fix,
  passes after, asserts the real behavior, and lives next to the code it
  guards.
- Hold scope: a bug-fix plan does not expand into a refactor; unrelated
  findings go under "NOT in scope" with a reason.

**Follow-up:** `/investigate` when the cause is still unknown at planning
time; plan-tier `/plan-eng-review` once the cause is proven;
post-implementation `/qa` (regression test) and `/review`.

## docs — documentation (`/docs-refresh`, `/document-generate`)

**Select when:** the task edits README / CLAUDE.md / AGENTS.md / changelog /
guides / API reference, or ships a feature whose docs must move with it.

- Refresh surgically instead of regenerating: preserve the existing voice and
  document structure. A docs change is not a license to rewrite.
- Pick the document type deliberately (tutorial, how-to, reference,
  explanation) and do not mix them in one page.
- Document the escape hatches next to the happy path; the reader who hits
  the edge case is the one who needs them most.
- Every documented command is copy-pasteable and verified to run as written;
  examples that no longer work are defects.
- Stale docs are a defect, not a chore: if a procedure no longer matches the
  code, the plan fixes the docs, not the other way around; a root `.md` that
  describes changed code is updated in the same change.
- Agent-facing docs (CLAUDE.md, AGENTS.md) state verify commands, conventions,
  and boundaries in imperative, testable sentences; keep them short enough to
  be read on every session.
- Changelog entries state user-visible impact and the version, never a list
  of files.

**Follow-up:** `/docs-refresh` for existing docs, `/document-generate` for
missing ones, `/document-release` after shipping.

## perf — performance (`/plan-eng-review`, `/benchmark`)

**Select when:** the task's goal is speed, latency, throughput, bundle size,
or resource usage: optimizing a slow path, adding caching, cutting memory, or
the instructions name a performance budget.

- Measure before and after: the plan's first perf step captures a baseline
  (timing, query count, memory, bundle bytes) and its last step re-runs the
  same measurement. A perceived speedup without numbers is not a result.
- Name the budget that makes this done (p95 < X ms, N queries, Y KB) and
  the regression threshold (timing +50% or +500ms, bytes +25% is a
  regression; frontend budgets FCP < 1.8s, LCP < 2.5s, JS < 500KB).
- Optimize the proven hot path only; every other cleanup is explicitly out of
  scope. Premature optimization steps are cut in review.
- Known killers to design out: N+1 (eager-load or batch), missing indexes on
  new WHERE/ORDER BY/foreign keys, O(n²) loops (`find` inside `map`),
  unbounded lists without pagination or LIMIT, fetch waterfalls (`Promise.all`),
  blocking I/O in async handlers, heavy dependencies for one call, barrel
  imports, missing code splitting.
- Caches need an invalidation story and a stampede story in the plan, or
  they are not planned.
- State the correctness guard: what test proves behavior is unchanged after
  the optimization (ordering preserved, races absent, cache coherent).

**Follow-up:** plan-tier `/plan-eng-review`; post-implementation
`/review --performance` and `/benchmark` (`--baseline` before, `--diff`
after, for web pages).

## ios — Apple platforms (`/ios-qa`, `/ios-design-review`, `/ios-fix`)

**Select when:** the task touches Swift / SwiftUI / UIKit / Xcode targets or
App Store delivery.

- Verify on a real device or simulator run, not just a build that compiles;
  a green build is not evidence of correct behavior.
- Respect platform HIG conventions over web idioms: navigation patterns,
  gestures, system controls, Dynamic Type, and chrome follow iOS, not a
  ported web design.
- Handle the app-lifecycle states explicitly (background, cold launch, low
  memory, permission prompts, offline); the plan names the behavior for each.
- Keep debug-bridge and test wiring out of release builds: `#if DEBUG`
  guards or separate targets, never a shipped debug path.
- Distribution is scope: signing, TestFlight, App Store metadata, and the
  minimum-OS decision are plan items or an explicit "NOT in scope".

**Follow-up:** plan-tier `/plan-eng-review`; post-implementation `/ios-qa`
(live device QA), `/ios-design-review`, `/ios-fix`.

## data — schema, migrations & data safety (`/plan-eng-review`, `/review --data-migration`)

**Select when:** the task adds or changes tables, columns, indexes,
constraints, ORM models, migrations, backfills, or moves data between stores.

- Every migration has a down path that actually undoes it; state plainly
  whether rollback loses data.
- Never drop or rename a column or table in the same deploy as the code
  that stops using it: deprecate, migrate readers, then remove; grep every
  ORM, raw SQL, view, and report reference first.
- NOT NULL or type-narrowing changes require a backfill first; new NOT NULL
  columns get a DEFAULT or a batched backfill step (never all rows in one
  statement on a large table).
- Lock discipline: `CONCURRENTLY` for indexes and ALTERs on tables past
  ~100K rows, one lock instead of several ALTERs, no exclusive locks at
  peak; name the expected lock duration.
- Indexes for every new foreign key and every new WHERE/ORDER BY; check for
  duplicates; prefer partial indexes when the predicate is selective.
- Sequence deploy and migrate explicitly ("deploy code first, then migrate"
  or the reverse) and guard the mixed old-code/new-schema window with a
  feature flag or dual-read; "old code + new schema = crash" is the failure
  to plan against.
- Constraints live in the database when the platform supports them (unique
  indexes, foreign keys, check constraints) rather than only in app code;
  find-or-create gets a unique index plus duplicate-key retry.
- Data classification travels with the schema: PII and secrets get their
  retention, encryption, and deletion path named.
- Verify with counts: the backfill step's Verify line compares row counts or
  checksums before and after.

**Follow-up:** plan-tier `/plan-eng-review`; post-implementation
`/review --data-migration` (never auto-gated off) and `/review --performance`.

## api — contracts & compatibility (`/plan-eng-review`, `/review --api-contract`)

**Select when:** the task adds or changes endpoints, routes, webhooks,
response shapes, SDKs, public interfaces, or anything consumed by clients the
team does not control.

- No removed or retyped response fields, new required parameters, changed
  methods or status codes, or tightened auth on an existing endpoint without
  a version bump or an alias; enumerate the clients that cannot force-update
  (mobile apps, SDK users, webhook subscribers).
- One versioning strategy (URL, header, or query), centralized; deprecations
  carry a sunset date and a migration note.
- Error envelope consistent with sibling endpoints (code, message, details,
  documentation link); status codes match the error class; no stack traces,
  SQL, or internal identifiers leak.
- Mutations are idempotent (idempotency keys or natural keys); IDs are
  prefixed and opaque; pagination is cursor-based or backward compatible,
  with total/next indicators.
- Rate limiting parity with sibling endpoints; payload limits stated;
  timeouts and retries documented for callers.
- Contract artifacts move with the code: OpenAPI/GraphQL schema, README
  examples, and generated clients are updated in the same step and the
  examples still run.
- Contract tests pin the shape: a test per endpoint asserts status, required
  fields, and error envelope for the success and the loudest failure case.

**Follow-up:** plan-tier `/plan-eng-review` (or `/plan-devex-review` when
developers are the consumers); post-implementation `/review --api-contract`
and `/devex-review`.

## ai — LLM, agents & tool use (`/plan-eng-review`, `/cso`)

**Select when:** the task builds or changes prompts, LLM calls, agents, tool
or function definitions, MCP servers, retrieval/RAG, embeddings, evals, or
code that executes model output.

- Model output is untrusted input: validate every generated value before it
  touches a database, mailer, shell, or filesystem (shape-check structured
  output, parse URLs and emails, strip and bound strings); allowlist any URL
  the model asks to fetch (SSRF); sanitize before storing in vector or
  knowledge stores (stored prompt injection).
- Never `eval`/`exec` model-generated code outside a sandbox; tool arguments
  are validated and authorized per user/tenant before execution; the model
  never holds credentials it does not need.
- Trace untrusted text (prompts, retrieved documents, tool results, memory)
  to every consequential tool it can reach and plan the envelope that keeps
  it data, not instructions; guard memory poisoning, uncontrolled
  delegation, and paid-work amplification (runaway loops, retries, spend).
- Prompt hygiene: single source of truth for limits and tool lists (the
  wired tools match the described ones), 1-indexed lists, explicit output
  contract, refusal and empty/malformed/invalid-JSON responses handled by
  name.
- Evals are the tests: a prompt or tool-definition change ships with an eval
  (golden cases, adversarial cases, a regression case) and a pass threshold;
  "it seemed better" is not a result.
- Cost and latency are budgets: model choice, max tokens, caching, streaming,
  and timeouts are decided in the plan with numbers.
- Observability: log prompt version, model, tokens, latency, and outcome per
  call (never raw secrets or PII); make failures diagnosable three weeks
  later.
- MCP and skill surfaces are code-bearing input: audience-bound auth, no
  token passthrough, confused-deputy checks, consent binding; treat
  SKILL.md/plugins/hooks as code and inspect their install path.

**Follow-up:** plan-tier `/plan-eng-review` (eval rule) and, for exposed
surfaces, `/cso`; post-implementation `/review --security` (the LLM output
trust boundary is a critical-pass category) and `/cso --code` or `--skills`.

## ops — deploy, CI/CD & operability (`/plan-eng-review`, `/land-and-deploy`, `/canary`)

**Select when:** the task touches CI/CD workflows, release/publish pipelines,
Docker/IaC, environment configuration, feature flags, monitoring, alerting,
cron/schedulers, or how the system is deployed and rolled back.

- Deployment is not atomic: plan the rollout order (schema, code, flags,
  data), the partial states in between, the rollback steps, and the deploy-
  time window; state what staging parity is required.
- Feature flags for anything user-visible or risky, with the flag's removal
  as a planned step, not a lingering branch.
- Post-deploy verification is a plan item: the smoke checks at 5 minutes and
  1 hour, the health endpoint, the dashboards or logs to watch, and the
  alert that fires when it goes wrong.
- Observability ships with the feature: structured logs with correlation
  ids, metrics for the new path, an alert with an owner; a bug reported
  three weeks later must be diagnosable from what was logged.
- CI is a trust boundary: no secrets inline (`${{ secrets.X }}` only),
  `pull_request_target` / `workflow_run` and shell interpolation of untrusted
  values scrutinized, caches not poisonable, pinned actions understood as
  reduced risk not trust.
- Distribution completeness: a publish workflow for every new artifact type,
  a CI matrix covering the target OS/arch, consistent tag format, idempotent
  publishing.
- Containers and infra default to least privilege: no root, no privileged
  mounts, no host networking, no wildcard IAM; preview and staging cannot
  reach production credentials.
- Configuration over hardcoding: env vars documented with defaults and
  validated at startup; missing config fails loudly at boot, not at 3am.
- Jobs and schedulers are idempotent, bounded (timeouts, retry caps, dead
  letters), and observable; "silently failing background job" is the failure
  to plan against.

**Follow-up:** plan-tier `/plan-eng-review` (deployment section);
post-implementation `/review` (distribution & CI/CD category), `/cso
--supply-chain` or `--infra`, then `/land-and-deploy` and `/canary`.

### Routing rules (for Step 9)

- The deterministic `route` subcommand (`code_plan.py route --instructions-file
  <enhanced> --json`) computes the baseline lens set. Run it first; its output
  is the floor.
- The model may add or drop **at most ONE** lens on top of the baseline, and
  only with a one-line justification shown in the Step 12 report. Never replace
  the whole set; never exceed 3 lenses.
- `--experts=<list>` forces the lens set verbatim (bypassing the router);
  `--experts=none` skips the step entirely. The router validates the ids.
- **"none" is a valid outcome** — generalist chores should not get force-fitted
  lenses.
- On conflicting lens advice (e.g. product says cut, eng says complete), the
  plan's Context section names the tension and makes the senior-engineer call.
- If a matched skill has no distillate entry here, borrow only its roster
  description as a one-line lens — do NOT read its full SKILL.md.
- No gstack installed / empty roster → generalist plan, say so in one line,
  continue. Expert selection is enrichment, never a dependency.

### Pre-planning routes (the router's `pre_skill`)

Some requests are not ready to be planned. The enhancement prompt marks those
with an **Open questions** section or a trailing `NOTE:`; the router then sets
`clarify: true` and `pre_skill: "spec"`. The plan is still written (under
stated assumptions, each recorded in Context), and the Step 12 report adds a
`before executing:` line:

| Request shape | Recommend first | Why |
|---|---|---|
| Ambiguous or contradictory requirements, missing acceptance criteria | `/spec` | Interrogates the request until it is a zero-design-decisions-left ticket with testable acceptance criteria |
| An idea whose worth is unproven ("should we build", "brainstorm", no named user) | `/office-hours` | Six forcing questions on demand, wedge, and status quo; ends in a decision record the plan can cite |
| "Think bigger", scope or ambition questions on a feature | `/plan-ceo-review` | Premise challenge, alternatives, scope posture, before the eng review |

### gstack hand-off contract notes

Behavioral facts about the follow-up skills, verified against gstack 1.87.4.0
by hand; the live snapshot in `prompts/gstack-contract.md` supersedes any
version-specific detail here. These change how a chained review behaves — not
which skill is recommended:

- **The scope gate auto-resolves a named target (gstack ≥ 1.62).** Only
  `plan-eng-review` and `plan-design-review` carry a scope gate ("branch diff /
  a plan or design doc / a path"). When the invocation explicitly names the
  review target (as code-plan's Step 14 `args` does — it passes the plan
  path), the gate skips its question and reviews that target directly; in
  plan mode it auto-selects the active plan. Only an *unnamed* target outside
  plan mode still hard-STOPs. On older gstack (1.58.4–1.61) the question
  always fires — supplying the answer in `args` pre-answers it either way.
- **`plan-ceo-review` and `plan-devex-review` have NO scope gate** — do not
  promise the user a target-confirmation question for those two.
- **Plan reviews edit the plan in place.** Every plan-tier review writes its
  required outputs into the plan file ("NOT in scope", "What already exists",
  diagrams, failure-mode registry, `## Implementation Tasks`, and a terminal
  `## GSTACK REVIEW REPORT` whose last line is `NO UNRESOLVED DECISIONS` or an
  unresolved-decisions list). A chained review that rewrites sections of the
  plan is doing its job; `/code-execute` still runs the file as it stands.
- **Plan reviews look for an upstream decision record first (gstack ≥ 1.65).**
  They read `docs/designs/<topic>.md` in the target repo (preferred over a
  gstack-side design doc when at least as fresh), `DESIGN.md`, and any
  `~/.gstack/projects/<slug>/*-design-*.md`; when none exists they offer to
  run `/office-hours` inline once. A plan that cites its decision record gets
  reviewed against it.
- **`autoplan` skips the scope gate entirely** and runs its phases in a fixed
  order: CEO → Design (if UI scope) → DX (if developer-facing scope) → Eng,
  always last, with one final approval gate on the fully amended plan (gstack
  ≥ 1.75). It auto-decides with six principles (choose completeness, boil
  lakes, pragmatic, DRY, explicit over clever, bias toward action); anything
  that would change the user's stated direction is queued as a User Challenge
  for the gate, never auto-decided. Its task aggregation is trustworthy only on
  gstack ≥ 1.65 (before that it emitted zero tasks while reporting success).
- **Outside voices are default-on (gstack ≥ 1.57.10, harness-aware since
  1.86).** Plan reviews, `/review`, and `/ship` run a Codex cross-model pass
  when the `codex` CLI is installed and authenticated, and fall back to a
  same-family Claude subagent otherwise (labelled honestly, not as
  cross-model coverage). Cross-model agreement is signal, never permission:
  a chained review presents tensions and asks; it never overrides the plan's
  stated direction on its own.
- **`/review` dispatches specialist subagents** (testing, maintainability,
  security, performance, data-migration, api-contract, simplification,
  red-team, plus a design checklist on frontend diffs) with force flags
  `--security`, `--performance`, `--testing`, `--maintainability`,
  `--data-migration`, `--api-contract`, `--design`, `--simplification`,
  `--all-specialists` (the live list is in the snapshot). It reviews a *diff*,
  so it is a post-implementation follow-up (after `/code-execute` +
  `/code-validation`), never a plan review. Diffs under 50 lines dispatch no
  specialists without a force flag; simplification is advisory only (gstack ≥
  1.75) and never cuts tests, error paths, or edge cases.
- **Review records bind to content (gstack ≥ 1.66.1, both ends since
  1.87.3).** A diff review captures the tree before reading it and compares
  again when done; fixes applied during the pass need another pass before the
  result counts as CURRENT. Plan-tier reviews (the ones code-plan chains) age
  by the clock (7-day freshness). `/ship` cites fresh recorded evidence
  instead of re-running suites.
- **Chained skills may run a live probe before declaring anything blocked
  (gstack ≥ 1.65)** — tier-2+ skills treat "the API can't do this" as a
  material claim requiring the verbatim error, a documented statement, or a
  ten-second check. Expect a chained review to challenge unverified "can't"s
  in the plan.
- **Accepted shortcuts leave a trail (gstack ≥ 1.75).** When a review accepts
  a lower-completeness option on a durable-scope call it logs the decision
  and expects a `gstack-shortcut(dec-<id>)` marker at the cut corner; `/retro`
  harvests them. A plan that records its own shortcuts under "Decisions to
  record" gives the review something to bind to.
- **Every gstack skill ends with a bounded closer and a durable-learnings
  line (gstack ≥ 1.68 / 1.75).** A chained skill's short "what changed, what
  was skipped, what to watch" plus "No durable learnings this session" is
  expected, not noise. Learnings land in `~/.gstack/projects/<slug>/
  learnings.jsonl`; code-plan's Step 8 reads them back on the next run.
- **A chained skill that asks no question is not broken** — gstack's 1.62+
  preamble allows a skill to resolve its own gate question silently, and a
  spawned/headless session auto-chooses the recommended option.

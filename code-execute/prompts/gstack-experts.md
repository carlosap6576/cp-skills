# gstack Expert Roster — post-implementation tier

Reference for `/code-execute`'s Step 3 (project signals), Step 4
(execution-time awareness) and Step 6 (expert-aware recommendation /
`--skill` chaining).
Verified against gstack 1.91.2.0 by hand (every post-implementation skill and
`/review`'s specialist checklists read in full). The **live, machine-verified
snapshot** is `$SKILL_DIR/prompts/gstack-contract.md` — regenerated by the
cp-skills installer every time gstack is installed or upgraded. It lists every
installed gstack expert with its description, `/review`'s current specialists,
force flags and thresholds, `/autoplan`'s phase order, and which plan reviews
carry a scope gate. **Read it first; where it disagrees with this file, it
wins.** The roster and routing tables below are worked examples, not a
whitelist: choose the installed expert that best suits what the work actually
touched — including experts gstack added after these examples were written —
and say in one line why it fits.

**This file is enrichment, never a dependency.** No gstack installed → the
default `/code-validation` recommendation stands alone; never block or warn
beyond one line. `/code-plan` owns the *plan-tier* lens distillates
(`code-plan/prompts/expert-lenses.md`); this file covers the
*implementation-tier* experts — the ones that act on written code, a working
tree, or a running app, which is what exists after this skill finishes.

## The roster

| Skill | What it is | Reach for it when |
|---|---|---|
| `/code-validation` | Sibling skill: audits the implementation against the plan item-by-item, FIXES gaps, tears down proof-only scaffolding, and deletes the plan on full success | **Always the default next step** after execution |
| `/review` | Pre-landing diff review: scope-drift check, plan-completion audit, critical pass (SQL/data safety, races, LLM trust boundary, shell injection, enum completeness), specialist subagents (below), adversarial pass, fix-first | The changes are about to land; broad or risky diffs |
| `/qa` | Live browser QA of a web app as a real user (diff-aware on a feature branch); **fixes** the bugs it finds, one atomic commit each, with a regression test per fix | The plan built user-observable web behavior |
| `/qa-only` | Same QA sweep, **report-only** (no fixes, no source reading) | You want findings without another skill editing code |
| `/cso` | Evidence-first security audit: supported findings need an attacker entrypoint, a crossed boundary, demonstrated impact and challenged controls; `--diff` scopes to the branch, `--comprehensive` adds sandboxed reproduction and repair candidates, `--code` / `--skills` / `--supply-chain` / `--infra` scope the phases | Execution touched auth, secrets, user input, uploads, subprocess, webhooks, LLM/agent tooling, CI/CD, or network-facing code |
| `/design-review` | Designer's-eye QA on the running page: screenshots at 375/768/1440, 10-category checklist with numeric floors (16px body, 4.5:1 contrast, 44px targets), deterministic anti-pattern detector, then CSS-first fixes with a risk budget | Execution touched UI components, pages, or styling |
| `/devex-review` | Live developer-experience audit: measured time-to-hello-world, error-message quality, docs findability; flags any dimension 2+ points below the plan's DX score | Execution built CLIs, tooling, SDKs, scripts, or install/setup flows |
| `/investigate` | Systematic root-cause debugging: reproduce first, falsifiable hypothesis, minimal fix, regression test that fails-then-passes, blast-radius check | Execution surfaced a failure it could not root-cause, or a `[MOCKED]` item hides a suspected real bug |
| `/benchmark` | Browser-measured web performance: TTFB/FCP/LCP, bundle bytes, request counts against budgets and a baseline (`--baseline` before, `--diff` after) | The plan had a perf goal or touched a hot path |
| `/health` | Code-quality dashboard wrapping the repo's own typecheck/lint/test/dead-code tools into a weighted score; read-only | A quality snapshot of the touched area is wanted |
| `/document-release` | Post-ship docs sync: coverage map of the diff against README/CLAUDE.md/CHANGELOG/TODOS, factual updates applied directly | Execution changed public behavior, commands, or config the docs describe |
| `/codex` | Outside-model second opinion (review / challenge / consult) on the diff | A cross-model read is wanted before landing |
| `/ship` | Landing workflow: merge base, run tests, review diff, plan-completion audit, version bump, CHANGELOG, commit, push, PR, auto `/document-release` — **runs git under its own contract** | Everything is validated and ready to land |
| `/land-and-deploy` · `/canary` | Merge + deploy + verify (needs `## Deploy Configuration` in CLAUDE.md from `/setup-deploy`; approval bound to the PR head and base); post-deploy monitoring against a baseline (alerts only after 2+ consecutive checks) | The plan touched deploy config, infra, or routes worth watching after release |

## `/review` specialist mechanics (gstack 1.64+, verified 1.91.2.0)

`/review` reviews the working-tree diff against the base branch, runs its own
critical pass, then dispatches specialist subagents in parallel. Knowing the
dispatch rules lets you predict — and force — coverage:

- **Always dispatched** (diff ≥ 50 lines): `testing` (negative paths, edge
  cases, isolation, flake patterns, security-enforcement tests) and
  `maintainability` (dead code, magic numbers, stale comments, DRY,
  conditional side effects, module boundaries).
- **Diff < 50 lines → ALL specialists are skipped** ("Small diff" notice).
  A tiny-but-risky change needs a force flag to get specialist eyes.
- **Scope-gated**: `security` (auth-path scope, or backend scope + >100
  lines), `performance` (backend or frontend scope), `data-migration`
  (migration files present), `api-contract` (API scope), `design` (frontend
  scope; checklist + mechanical detector), `simplification` (diff > 100
  lines; advisory only — its rows flag unrequested structure with a closed
  vocabulary `delete:` / `stdlib:` / `native:` / `speculative:` / `shrink:`,
  never block, never cut tests or error paths).
- **Adaptive gating**: a conditional specialist with 0 findings in 10+ past
  dispatches is auto-gated OFF — except `security` and `data-migration`,
  which are `[NEVER_GATE]` insurance policies.
- **`red-team`**: activates only when the diff exceeds 200 lines OR any
  specialist reported a CRITICAL finding; it attacks the already-reviewed
  code (10x load, simultaneous requests, slow DB, garbage from external
  services, silent partial failures, trust assumptions, double-click) and
  merges extra findings. No force flag summons it.
- **Adversarial pass is always on** (≥ 1.57.10): a Claude adversarial
  subagent every time, plus a Codex pass when the `codex` CLI is ready; a
  Codex structured review with a P1 gate on diffs ≥ 200 lines.
- **Force flags** (put them in the `args` when chaining): `--security`,
  `--performance`, `--testing`, `--maintainability`, `--data-migration`,
  `--api-contract`, `--design`, `--simplification`, `--all-specialists` — each
  force-includes its specialist regardless of scope and gating.
- **Plan-completion audit**: `/review` (and `/ship`) discover the plan from
  the conversation or `~/.gstack/projects/<slug>` and classify every
  actionable plan item DONE / PARTIAL / NOT DONE / CHANGED / UNVERIFIABLE; a
  concrete path must be DONE or NOT DONE, never "unreachable". Name the plan
  path in `args` so the audit reads the right file.
- **Freshness binds to content (≥ 1.87.3)**: the review captures the tree
  before reading it and compares when done; fixes applied during the pass
  need another pass before the result counts as CURRENT.
- **Shared-code check runs on every diff (≥ 1.89)**, including diffs under
  50 lines and hosts without specialists: it needs ≥ 2 verified authored
  callers (at least one changed in this diff), reuses existing helpers
  first, and emits extractions as `[ADVISORY]` rows — ASK-only, never
  auto-applied, excluded from the quality score and clean status, never
  able to suppress a real defect. The maintainability specialist now reports
  only *duplicated behavior with defects* (divergent copies that produce a
  wrong result); matching syntax alone is not a finding.
- **Claims need citations**: "safe" cites the line, "handled elsewhere"
  cites the handler, "tests cover this" names the test file and method.
  Findings under confidence 5 drop to an appendix or are suppressed.
- **Coverage diagrams are drawn from read files (≥ 1.87.6)**: the testing
  specialist reads the named source and test files before mapping
  `[OK]`/`[GAP]` rows, one root per changed public function.
- `/review` edits code (AUTO-FIX directly, ASK items after approval) but never
  commits, pushes or opens a PR.
- Since gstack 1.67 its checklists resolve from the installed skill root, so
  it works in ANY target repo (before that, only inside gstack's checkout).

Practical rule: when chaining `/review` after a security-, migration-, API-,
or UI-relevant execution, append the matching force flag(s) in `args` rather
than trusting scope detection.

## Routing table — what execution touched → which expert to name

Used by Step 6's advisory (pick at most TWO rows; the `/code-validation`
line always comes first). Judge "touched" from the files the plan actually
changed, not from the plan's aspirations.

| Execution touched | Recommend (after validation) |
|---|---|
| Auth, secrets, user input, subprocess, network-facing code | `/cso --diff` (evidence-first audit) — or `/review --security` when a diff-scoped pass is enough |
| LLM calls, prompts, tool/function definitions, MCP servers, agent loops | `/review --security` (LLM output trust boundary is a critical-pass category); `/cso --code` or `--skills` for exposed surfaces |
| UI components, pages, styling, interaction flows | `/design-review`; add `/qa` if the flow is user-walkable |
| User-observable web behavior (a flow, a page, an endpoint UI) | `/qa` (fixes, regression tests) or `/qa-only` (report only) |
| CLI, tooling, scripts, install/setup, developer-facing APIs or SDKs | `/devex-review` |
| DB schema or data migrations, backfills | `/review --data-migration` (never auto-gated off); `--performance` when indexes or large tables are involved |
| Public/consumed API surface, webhooks, response shapes | `/review --api-contract` |
| A refactor, new abstraction, or new dependency | `/review --simplification --maintainability` (advisory `net: -N lines possible`) |
| The same logic or fix now lives in several places | `/review` (shared-code advisory on the diff); `/deslop-shared-libs` for the repo-wide sweep |
| Swift / SwiftUI / Xcode targets | `/ios-qa` (device QA); `/ios-design-review` for UI; `/ios-clean` before a release build |
| An LLM model choice or prompt cost/latency budget | `/benchmark-models` |
| Web flow behind a sign-in | `/setup-browser-cookies` before `/qa` |
| A perf target the plan named | `/benchmark` (`--baseline` before, `--diff` after) |
| CI/CD workflows, release/publish pipelines, Docker/IaC, deploy config | `/review` (distribution & CI/CD category); `/cso --supply-chain` or `--infra`; `/land-and-deploy` + `/canary` once validated (`/setup-deploy` first when unconfigured) |
| README / CLAUDE.md / CHANGELOG-visible behavior | `/document-release` |
| Large diff (>200 lines) or several subsystems | `/review` (red team and the Codex structured gate self-activate at this size) |
| `[MOCKED]` items masking a suspected real defect, or an unexplained failure | `/investigate` |
| Clean, validated, ready to land | `/ship` |

## Execution-time awareness (facts that change how Step 4 behaves)

- **Verification evidence binds to tree content (gstack ≥ 1.66.1; both ends
  since 1.87.3).** A "tests pass" claim is only citable for the exact tree
  it ran on — any edit afterward voids it. Consequence for the executor: run
  the FINAL full verification pass after the LAST edit, never before;
  `/ship` and `/review` will re-run anything the tree has outgrown, so a
  final-pass-then-tweak ordering wastes the evidence.
- **The repo may declare its verify command.** A `<!-- gstack:verify: <cmd>
  -->` line in CLAUDE.md is the command the repo trusts; run it in the final
  pass. If the user armed `gstack-verify-gate` (opt-in Stop hook, ≥ 1.65),
  the turn cannot end until it passes — run the declared command and fix; do
  not treat the block as a harness bug.
- **Guardrails fail closed (gstack ≥ 1.66.1).** `/freeze`/`/guard` deny
  edits outside their boundary (including symlink escapes), `/investigate`
  auto-freezes the affected directory, and `/careful`'s HIGH tier hard-denies
  `rm -rf /`-class deletes and default-branch force pushes. A denied tool
  call during execution may be a deliberate guardrail: report which step is
  blocked and by what; never work around it.
- **Claimed limitations need evidence (gstack ≥ 1.65).** Declaring a backend
  "unreachable" or an API "can't do this" is a material claim — the
  execute-prompt's single reachability probe IS that evidence; cite its
  verbatim failure next to each `[MOCKED]` flag. A chained review re-probes
  unverified "can't"s.
- **The pre-landing review hunts over-built code (gstack ≥ 1.75).** The
  simplification specialist flags one-implementation abstractions,
  hand-rolled stdlib, dependencies duplicating platform features, and dead
  flexibility; the reuse ladder in the execute prompt exists so there is
  nothing for it to find. Completeness and simplification are orthogonal:
  coverage up, unrequested structure down.
- **Accepted shortcuts leave a trail (gstack ≥ 1.75).** If the plan's
  "Decisions to record" names a deliberate shortcut, gstack expects a
  `gstack-shortcut(dec-<id>): <ceiling>, upgrade when <trigger>` marker at
  the cut corner and a decision-ledger entry; `/review` treats a marker with
  no ledger entry as a forged suppression. Do not invent markers; only carry
  the ones the plan records.
- **Design work is calibrated against `DESIGN.md` (gstack ≥ 1.84).** When the
  repo has an open-format `DESIGN.md`, a value present in its tokens is never
  a finding; values that drift from it are. Use its tokens, type scale,
  spacing, and motion rules verbatim in any UI step.
- **Landing is evidence-bound (gstack ≥ 1.90.2).** `/land-and-deploy`
  accepts only CURRENT diff reviews and fresh test evidence, binds approval to
  the exact PR head and base branch, and reports `DEPLOYED AND VERIFIED` only
  when the new revision is proven live — a healthy old page is not proof.
  `/ship` makes no WIP checkpoint commits (≥ 1.89.1) and sends late fixes
  back through fresh tests and review. Anything edited after the final
  verification is exactly what these gates will reject.
- **Extraction advice is not a defect (gstack ≥ 1.89).** Do not perform a
  broad shared-code extraction the plan did not ask for; `/review` will raise
  it as an ASK-only advisory and `/deslop-shared-libs` owns the repo-wide
  sweep. Divergent copies that already produce a wrong result ARE defects.
- **Chained-skill behaviors that are NOT bugs:** a chained gstack skill may
  resolve its own gate questions silently when the target is named in `args`
  (≥ 1.62), may run a live probe before accepting a "can't" (≥ 1.65), runs an
  outside-model voice by default and falls back to a Claude subagent
  (≥ 1.57.10, harness-aware ≥ 1.86), and ends with a bounded closer plus an
  explicit durable-learnings line even when there are none (≥ 1.68 / 1.75).
  `/review` spawns subagents, `/qa` and `/design-review` commit their fixes,
  and `/ship` runs git — each under its OWN contract; code-execute's laws end
  at the hand-off.

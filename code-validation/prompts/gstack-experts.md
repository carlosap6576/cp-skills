# gstack Expert Roster — validation tier

Reference for `/code-validation`'s Step 4 (audit-time awareness) and Step 6
(expert-aware recommendation / `--skill` chaining).
Verified against gstack 1.87.4.0 by hand (every post-implementation skill and
`/review`'s specialist checklists read in full). The **live, machine-verified
snapshot** is `$SKILL_DIR/prompts/gstack-contract.md` — regenerated by the
cp-skills installer every time gstack is installed or upgraded. It lists every
installed gstack expert with its description, `/review`'s current specialists,
force flags and thresholds, `/autoplan`'s phase order, and which plan reviews
carry a scope gate. **Read it first; where it disagrees with this file, it
wins.** The roster and routing tables below are worked examples, not a
whitelist: choose the installed expert that best suits what the work actually
touched — including experts gstack added after these examples were written —
and say in one line why it fits.

**This file is enrichment, never a dependency.** No gstack installed → the
plain `next: /review — …` advisory stands (or is dropped if even /review is
absent); never block or warn beyond one line. `/code-plan` owns the
*plan-tier* lens distillates; `/code-execute` carries the implementation-tier
twin of this file. This one is tuned to validation's seat in the lifecycle:
the code is already written AND audited/fixed when Step 6 runs, so the
experts here are the pre-landing and landing tier.

## The roster

| Skill | What it is | Reach for it when |
|---|---|---|
| `/review` | Pre-landing diff review: scope-drift check, plan-completion audit, critical pass (SQL/data safety, races, LLM trust boundary, shell injection, enum completeness), specialist subagents (below), adversarial + outside-model pass, fix-first | **The default next step** after a validated audit — the diff is exactly what it wants |
| `/ship` | Landing workflow: merge base, run tests, review diff, plan-completion audit, version bump, CHANGELOG, commit, push, PR, auto `/document-release` — **runs git under its own contract** | The validated diff is clean and ready to land |
| `/qa` | Live browser QA of a web app as a real user; **fixes** the bugs it finds with a regression test per fix | The audited work is user-observable web behavior |
| `/qa-only` | Same QA sweep, **report-only** (no fixes) | You want findings without another skill editing the just-validated code |
| `/cso` | Evidence-first security audit (`--diff` for the branch; `--comprehensive` adds sandboxed reproduction and repair candidates; `--code` / `--skills` / `--supply-chain` / `--infra` scope it) | The audit's fixes touched auth, secrets, user input, uploads, subprocess, webhooks, LLM/agent tooling, CI/CD, or network-facing code and a diff-scoped `--security` pass is not enough |
| `/design-review` | Designer's-eye QA on the running page: screenshots at three viewports, numeric floors, anti-pattern detector, DESIGN.md calibration, then CSS-first fixes | The audited work touched UI components, pages, or styling |
| `/devex-review` | Live developer-experience audit with measured time-to-hello-world and error-message quality | The audited work is CLIs, tooling, SDKs, scripts, or install/setup flows |
| `/investigate` | Systematic root-cause debugging: reproduce first, falsifiable hypothesis, minimal fix, fails-then-passes regression test | A Residual-risk item hides a suspected real defect the audit could not reach |
| `/benchmark` | Browser-measured web performance against budgets and a baseline | The plan had a perf target the audit should be held to |
| `/health` | Code-quality dashboard wrapping the repo's own typecheck/lint/test/dead-code tools; read-only | A quality snapshot of the touched area is wanted |
| `/document-release` | Post-ship docs sync driven by the diff's coverage map | The validated change altered documented behavior, commands, or config |
| `/codex` | Outside-model second opinion (review / challenge / consult) on the diff | A cross-model read is wanted before landing |
| `/land-and-deploy` · `/canary` | Merge + deploy + verify, then post-deploy monitoring against a baseline | Deploy config or watched routes changed and the diff has landed |

**Phase-5 sharpeners** (invoked DURING the audit, not chained after it): the
built-in `/simplify` (reuse/efficiency cleanup of the changed code) and
gstack `/review` (its simplification specialist names one-implementation
abstractions, hand-rolled stdlib, and dead flexibility with a `net: -N lines
possible` footer) may sharpen the cleanup sweep — LAW 1 still binds: no
helper's suggestion ever justifies git, and no helper's advice ever removes
tests, error paths, or edge cases.

**Wrong tier here:** `plan-eng-review`, `plan-design-review`,
`plan-ceo-review`, `plan-devex-review`, and `autoplan` review *plans*. The
plan is about to be DELETED by the LAW 6 close-out — never recommend a
plan-tier review from this skill.

## `/review` specialist mechanics (gstack 1.64+, verified 1.87.4.0)

`/review` reviews the working-tree diff against the base branch, runs its own
critical pass, then dispatches specialist subagents in parallel. Since the
Step 6 advisory recommends it by default, knowing the dispatch rules lets the
advisory name the force flags that guarantee the right coverage:

- **Always dispatched** (diff ≥ 50 lines): `testing` (negative paths, edge
  cases, isolation, flake patterns, security-enforcement tests) and
  `maintainability` (dead code, magic numbers, stale comments, DRY,
  conditional side effects, module boundaries).
- **Diff < 50 lines → ALL specialists are skipped** ("Small diff" notice).
  A small-but-risky validated diff needs a force flag to get specialist eyes.
- **Scope-gated**: `security` (auth-path scope, or backend scope + >100
  lines), `performance` (backend or frontend scope), `data-migration`
  (migration files present), `api-contract` (API scope), `design` (frontend
  scope; checklist + mechanical detector), `simplification` (diff > 100
  lines; advisory only — closed vocabulary `delete:` / `stdlib:` / `native:`
  / `speculative:` / `shrink:`, never blocks, never cuts tests or error paths).
- **Adaptive gating**: a conditional specialist with 0 findings in 10+ past
  dispatches is auto-gated OFF — except `security` and `data-migration`,
  which are `[NEVER_GATE]` insurance policies.
- **`red-team`**: activates only when the diff exceeds 200 lines OR any
  specialist reported a CRITICAL finding; it attacks the already-reviewed
  code and merges extra findings. No force flag summons it.
- **Adversarial pass is always on** (≥ 1.57.10): a Claude adversarial
  subagent every time plus a Codex pass when the CLI is ready; a Codex
  structured review with a P1 gate on diffs ≥ 200 lines.
- **Force flags** (append to the advisory line or the chained `args`):
  `--security`, `--performance`, `--testing`, `--maintainability`,
  `--data-migration`, `--api-contract`, `--design`, `--simplification`,
  `--all-specialists` — each force-includes its specialist regardless of scope
  and gating.
- **Plan-completion audit**: `/review` and `/ship` classify every actionable
  plan item DONE / PARTIAL / NOT DONE / CHANGED / UNVERIFIABLE. The plan is
  deleted by this skill's close-out, so a chained `/review` gets the plan
  path in `args` while it still exists, and a later manual `/review` relies
  on the Phase-6 traceability matrix instead.
- **Freshness binds to content (≥ 1.87.3)**: fixes applied during the review
  need another pass before the result counts as CURRENT; a stopped or
  non-converged run never clears the code-review row.
- Since gstack 1.67 its checklists resolve from the installed skill root, so
  it works in ANY target repo (before that, only inside gstack's checkout).

## Routing table — what the audit's fixes touched → what to recommend

Used by Step 6's advisory: the `/review` line comes first, carrying every
matching force flag; at most ONE extra expert line follows. Judge "touched"
from the files the audit actually fixed or filled, not from the plan's
aspirations.

| The audit's fixes touched | Advisory addition |
|---|---|
| Auth, secrets, user input, subprocess, network-facing code | `--security` on the /review line; `/cso --diff` as the extra line when the surface is broad |
| LLM calls, prompts, tool definitions, MCP, agent loops | `--security` on the /review line (LLM output trust boundary is a critical-pass category); `/cso --code` or `--skills` as the extra line for exposed surfaces |
| DB schema or data migrations, backfills | `--data-migration` on the /review line (add `--performance` for indexes or large tables) |
| Public/consumed API surface, webhooks, response shapes | `--api-contract` on the /review line |
| UI components, pages, styling | `--design` on the /review line; `/design-review` as the extra line for a live visual pass |
| User-observable web behavior | `/qa` (fixes) or `/qa-only` (report only) as the extra line |
| CLI, tooling, scripts, install/setup flows, SDKs | `/devex-review` as the extra line |
| A refactor, new abstraction, or new dependency the audit kept | `--simplification --maintainability` on the /review line |
| A perf target the plan named | `/benchmark` as the extra line |
| CI/CD, release pipelines, Docker/IaC, deploy config | `/cso --supply-chain` or `--infra` as the extra line; `/land-and-deploy` once landed |
| Documented behavior, commands, or config | `/document-release` as the extra line |
| Residual risk hiding a suspected real defect | `/investigate` as the extra line |
| Diff under 50 lines but risk-bearing | The matching force flag(s) — without them /review dispatches NO specialists at this size |
| Clean and ready to land | `/ship` as the extra line |

## Audit-time awareness (facts that change how Step 4 behaves)

- **Verification evidence binds to tree content (gstack ≥ 1.66.1; both ends
  since 1.87.3).** A "tests pass" claim is only citable for the exact tree
  it ran on — any edit afterward voids it. The Phase-5 post-sweep
  re-verification is therefore the run that matters: it comes after the
  LAST edit, so its green is the citable one. `/ship` and `/review` re-run
  anything the tree has outgrown, so a verify-then-tweak ordering wastes the
  evidence.
- **The repo may declare its verify command.** A `<!-- gstack:verify: <cmd>
  -->` line in CLAUDE.md is the command the repo trusts; Phase 4 and the
  post-sweep re-verification both run it. If the user armed
  `gstack-verify-gate` (opt-in Stop hook, ≥ 1.65), the turn cannot end until
  it passes — run the declared command and fix; do not treat the block as a
  harness bug.
- **Residual risks need evidence (gstack ≥ 1.65).** Declaring a service
  "unreachable" or an API "can't do this" is a material claim — cite the
  verbatim probe output or error next to each Residual-risk item; a chained
  gstack skill may re-probe and challenge an unverified "can't".
- **The pre-landing review hunts over-built code (gstack ≥ 1.75).** Its
  simplification specialist flags one-implementation abstractions,
  hand-rolled stdlib, dependencies duplicating platform features, and dead
  flexibility, and its completeness-gap rule flags shortcuts where the
  complete version costs under 30 minutes. Phase 3's simplify-and-complete
  pass exists so it finds neither. Coverage and simplification are
  orthogonal: coverage up, unrequested structure down.
- **Accepted shortcuts leave a trail (gstack ≥ 1.75).** A
  `gstack-shortcut(dec-<id>): <ceiling>, upgrade when <trigger>` marker is
  acknowledged debt only when its decision id resolves in gstack's ledger;
  an orphan marker is reported as a forged suppression. The zero-comment
  sweep keeps a marker only when the plan's Decisions to record called for
  it; it never invents one.
- **Design work is calibrated against `DESIGN.md` (gstack ≥ 1.84).** A value
  present in its tokens is never a finding; values that drift from it are.
  When the audit touches UI, measure against the tokens, type scale, spacing,
  and motion rules in that file.
- **Guardrails fail closed (gstack ≥ 1.66.1).** `/freeze`/`/guard` deny
  edits outside their boundary (including symlink escapes), and `/careful`'s
  HIGH tier hard-denies `rm -rf /`-class deletes and default-branch force
  pushes. A fix denied by a guardrail is reported (which item, blocked by
  what), never worked around — it lands in Residual risks if it cannot be
  fixed inside the boundary.
- **Chained-skill behaviors that are NOT bugs:** a chained gstack skill may
  resolve its own gate questions silently when the target is named in `args`
  (≥ 1.62), may run a live probe before accepting a "can't" (≥ 1.65), runs an
  outside-model voice by default and falls back to a Claude subagent
  (≥ 1.57.10, harness-aware ≥ 1.86), and ends with a bounded closer plus an
  explicit durable-learnings line even when there are none (≥ 1.68 / 1.75).
  `/review` spawns subagents, `/qa` and `/design-review` commit their fixes,
  and `/ship` runs git — each under its OWN contract; code-validation's laws
  end at the hand-off (but LAW 6's close-out still runs afterward, in Step 7).

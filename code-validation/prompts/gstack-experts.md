# gstack Expert Roster — validation tier

Reference for `/code-validation`'s Step 4 (audit-time awareness and the
rubrics the audit applies itself) and Step 6 (advisory and `--skill` chaining).
Verified against gstack 1.99.1.0 by hand. The **live, machine-verified
snapshot** is `$SKILL_DIR/prompts/gstack-contract.md`, regenerated by the
cp-skills installer whenever gstack is installed or upgraded: every invokable
gstack expert with its description and chain-safety scan, the retired and
not-invokable skills, and `/review`'s specialists, flags and thresholds.
**Read it first; where it disagrees with this file, it wins.** The tables
below are worked examples, not a whitelist: choose the invokable expert that
best suits what the work actually touched, including one gstack added after
this file was written, and say in one line why it fits.

**This file is enrichment, never a dependency.** No gstack installed →
the
advisory is dropped and the audit runs on its own rubric; never block or warn beyond one line.

## The roster

The code is written, audited, fixed and proven when Step 6 runs, so the
experts here are the pre-landing and landing tier.

| Skill | What it is | Reach for it when |
|---|---|---|
| `/review` | Pre-landing diff review with specialist subagents and an adversarial outside voice; fix-first | **The default advisory**: a second, independent read before landing, on a feature branch |
| `/cso` | Evidence-first security audit (`--diff` scopes it to the change) | The audited change touched auth, secrets, user input, uploads, subprocess, webhooks, LLM/agent tooling, CI/CD, or network-facing code |
| `/qa-only` | Report-only QA of a browser, API, CLI, job, worker or webhook surface | The audited work is observable behavior and a live walk adds evidence |
| `/verify` | The repo's declared checks plus the pre-ship test selection, until green; no git | An independent green on the final tree is wanted before `/ship` |
| `/design-review` | Rendered-UI audit; `--build <preview url>` never commits or asks | The audited work touched UI |
| `/devex-review` | Live developer-experience audit | The audited work is CLIs, tooling, SDKs, or install flows |
| `/benchmark` | Browser-measured performance against budgets and a baseline | The plan named a perf target |
| `/test-audit` · `/deslop-shared-libs` · `/health` | Low-value tests · shared-code opportunities · quality dashboard; all read-only | Repetition or suite quality around the change is in question |
| `/codex` | Outside-model second opinion; never modifies files | A cross-model read is wanted before landing |
| `/ship` · `/land-and-deploy` · `/canary` · `/document-release` · `/qa` | Landing, deploy, post-deploy watch, docs sync, fixing QA — all human-run | The person landing the change wants them |

**Retired in gstack 1.98 — never name them:** the standalone root-cause
debugging skill and the standalone eng plan review were cut after evals found
no gain. A failure is now handled inline: one read-only check of the cause;
when it is still unclear, a focused test that fails on the bug before any
edit; then the root-cause fix and a rerun. The eng review lives on as
`/autoplan`'s eng phase. A crew-controller skill exists only on Capy machines.
The snapshot lists what is retired and what is not invokable on this machine.

**No helper skill edits the tree during the audit.** The audit applies the
rubrics below itself. A skill that edits or fetches after the final
verification voids the citable green.

## Chain safety — what the pipeline may invoke by itself

The pipeline runs unattended and never writes git, so an expert is chained
only when it neither waits for a person nor commits, pushes, merges, stashes
or rebases. The snapshot's "Chain safety scan" column is the mechanical check
on the installed version; when it flags a skill as a git writer, that wins
over this table.

| Tier | Skills | Rule |
|---|---|---|
| Chain-safe | `/verify`, `/qa-only`, `/cso`, `/deslop-shared-libs`, `/test-audit`, `/health`, `/design-review` with `--build` | May be chained by `--skill`. No git writes; no question when the target is unambiguous and the session kind is `spawned` |
| Explicit-only | `/review` | Chained only when the user named it. It runs `git fetch origin <base>`, edits source (AUTO-FIX), may post PR replies when a PR exists, and exits with "Nothing to review" when the checkout is on the base branch |
| Human-run | `/qa`, `/design-review` (default mode), `/document-release`, `/document-generate`, `/ship`, `/land-and-deploy`, `/canary`, `/modernize`, `/ios-fix`, `/ios-sync`, `/spec`, `/write-skill`, `/retro` | Never chained. They commit, push, merge, deploy, restore, or need a person at a gate. Print `run yourself: /<skill> — <why>` |

How unattended gstack runs resolve their own questions: the session kind is
read only from the `gstack-skill-start` preamble (`SESSION_KIND:` echo), never
from prompt text. `GSTACK_SESSION_KIND=spawned` prefixed on that command makes
a skill take its recommended option and never a destructive one;
`unattended` leaves consents and approval gates pending; `headless`
(`GSTACK_HEADLESS`, `CI`) makes a question BLOCK, so never rely on it. There
is no `--yes`/`--auto` flag on any gstack skill.

Expert-specific prerequisites:
- `/verify` asks once for consent to run repo commands unless its runner gets
  `--allow-repo-commands`; it stops after 5 runs or when the same failure
  returns twice, and never weakens a test or checker config to get green.
- `/cso` needs its compiled launcher; its scanners run in Docker and degrade
  to a static audit without it. Scopes are mutually exclusive: `--code`,
  `--infra`, `--skills`, `--supply-chain`, `--owasp`, `--scope <domain>`;
  modifiers `--diff`, `--base <ref>`, `--offline`, `--paths <p,q>`;
  `--comprehensive` adds reproduction and repair candidates.
- `/qa-only` covers browser, API, CLI, job, worker and webhook surfaces
  (`--quick`, `--regression <baseline>`); it never commits and works on a
  dirty tree. `/qa` is the fixing twin: it requires a clean tree and commits
  each fix.
- `/design-review --build <preview url>` runs on loopback only, never commits,
  stashes or asks, and stops editing after three rounds; the default mode
  requires a clean tree and commits each fix.
- `/health` asks nothing only when CLAUDE.md has a `## Health Stack` section.
- `/test-audit` is report-only when spawned; `/deslop-shared-libs` never
  writes anything.

## `/review` mechanics (verified 1.99.1.0)

`/review` diffs the working tree and untracked source against
`git merge-base origin/<base> HEAD`, so uncommitted work is covered, but only
on a feature branch. It never commits, pushes or opens a PR. Knowing its
dispatch rules lets the advisory name the flags that guarantee coverage:

- **Core pass on every diff**: SQL and data safety, races and concurrency, LLM
  output trust boundary, shell injection, enum and value completeness, gate
  integrity (a removed test, a suppression pragma, a relaxed gate value, a
  swallowed exception are always ASK findings), plus the shared-code check,
  an exploratory QA smoke, and the adversarial pass.
- **Always dispatched at 50+ changed lines**: `testing` and `maintainability`.
- **Under 50 lines every specialist is skipped except `state-machines`.** A
  small but risky change needs a force flag to get specialist eyes.
- **Scope-gated**: `security` (auth scope, or backend scope and more than 100
  lines), `performance` (backend or frontend scope), `data-migration`
  (migration files), `api-contract` (API scope), `design` (frontend scope,
  checklist-driven), `simplification` (more than 100 lines; advisory only,
  tags `delete` / `stdlib` / `native` / `speculative` / `shrink`, never cuts
  tests, error paths, validation, security or accessibility),
  `state-machines` (state-machine scope true or unknown).
- **`red-team`** activates past 200 lines or after any CRITICAL finding. No
  flag summons it.
- **`targeted`** (money, gate, auth and secret code: a paid call without a
  cap, a check that fails open, a verdict bound to the wrong commit, a secret
  written to logs or child args) is dispatched by `/ship`'s review plan, not
  by a force flag.
- **Adaptive gating**: a conditional specialist with 0 findings in 10+
  dispatches is skipped, except `security` and `data-migration`
  (`[NEVER_GATE]`).
- **Force flags** (in `args`): `--security`, `--performance`, `--testing`,
  `--maintainability`, `--data-migration`, `--api-contract`, `--design`,
  `--simplification`, `--state-machines`, `--all-specialists`.
- **Depth follows risk, not size** (light / standard / full); at most 2 review
  rounds and 3 fix cycles.
- **Fix-first**: dead code, N+1, stale comments, magic numbers and missing LLM
  output validation are edited in directly; security, races, design
  decisions, fixes over 20 lines, removed functionality and every gate
  finding are ASK items (left open when spawned).
- **Freshness binds to content**: the tree is captured before and after; an
  edit during the pass, or a fix-range re-review, never counts as CURRENT.
  Keep the tree frozen while reviewers run.
- **Shared-code check on every diff**: needs 2+ verified first-party callers,
  reuses existing helpers first, and emits extractions as `[ADVISORY]` rows
  that are ASK-only and never lower the score. Maintainability reports only
  duplicated behavior that already produces a wrong result.
- **Plan-completion audit**: every actionable plan item is DONE / PARTIAL /
  NOT DONE / CHANGED / UNVERIFIABLE; name the plan path in `args`.
- **Claims need citations**: "safe" cites the line, "tests cover this" names
  the test. Findings under confidence 5 drop to an appendix.

## Rubrics the audit applies itself

`/review` cannot run inside the audit (it needs a feature branch and fetches),
so Phase 2 and Phase 3 carry its specialists' checks directly. Apply each one
whose ground the change touched:

- **testing** — every error, guard and denied path has a test; boundaries
  (zero, negative, empty, null, single element, unicode); no shared state,
  clock, locale, network or order dependence; no sleeps; a new test answers
  what it protects, which regression fails it, and why existing coverage
  misses it.
- **security** — unvalidated input at handlers; uploads without type and size
  checks; unsigned webhooks; missing auth middleware; default-allow checks;
  object access without an ownership or tenant check; role escalation;
  unchecked token expiry; command, template, SSRF, path and header injection;
  weak hashes, `Math.random` tokens, non-constant-time comparison; secrets in
  code, logs or URLs; XSS escape hatches; unsafe deserialization.
- **targeted (money, gate, auth, secret)** — a paid call without a cap, a cap
  checked after the spend or in the wrong unit, a check that fails open, a
  loosened threshold, a verdict bound to the wrong commit, a token accepted
  after revocation, a secret written to logs or child arguments, a removed
  redaction.
- **performance** — queries in loops; a new WHERE or ORDER BY without an
  index; quadratic patterns; fetch waterfalls; unbounded list endpoints;
  heavy dependencies and barrel imports; sync I/O or sleep in async code.
- **data-migration** — a real rollback; drops or type narrowing that lose
  data; NOT NULL without a backfill; index or ALTER without `CONCURRENTLY` on
  tables past 100K rows; unbatched backfills; old code against new schema.
- **api-contract** — removed or retyped fields; new required params; changed
  methods, status codes or auth; a breaking change without a version bump;
  inconsistent error shape; missing rate limit or pagination; schema and docs
  drift.
- **state-machines** — build the kind × action matrix, write the expected
  resulting row from each kind's meaning, and map every cell to a test that
  asserts that row; an untested cell, a wrong row and collapsed kinds are all
  critical.
- **red team** (changes past 200 lines or after any critical finding) — 10x
  load, simultaneous requests, a 5-second database, garbage from an external
  service, swallowed exceptions, partial completion, frontend-only validation,
  max / zero / first-run inputs, a double click inside 100 ms.
- **gate integrity** — the change removed a test, added a suppression pragma,
  relaxed a gate value, or swallowed an exception. Restore it unless the plan
  ordered it.
- **design** — body under 16px, contrast under 4.5:1, targets under 44px,
  `outline: none` without a replacement, `transition: all`, more than three
  font families, skipped heading levels, and the slop tells (accent
  left-border cards, gradient text, purple gradients, centered everything,
  uniform large radius, generic hero copy). `DESIGN.md` values are never
  findings.
- **shared code** — fix duplication the implementation introduced inside this
  change (the executor rewrote a helper that exists → call the existing one).
  Do not extract across code the plan did not touch: that is advice for
  `/deslop-shared-libs`, not a defect. Divergent copies that produce a wrong
  result are defects.
- **verification** (from `/verify`) — command source order: CLAUDE.md
  `gstack:verify:`, then its `## Health Stack`, then the manifests; never
  invent a command the repo does not declare; only a pass is green; a failure
  is pre-existing only if it was red before any edit; never weaken, skip,
  delete or edit a test, a checker config or a script to get green.
- **failures** (the rule that replaced the retired debugging skill) — one
  read-only check of the cause; when it is still unclear, a focused test that
  fails on the bug before any edit; then the root-cause fix and a rerun. One
  guard in the shared function beats a guard in every caller.
- **observable behavior** (from the QA experts) — the final business effect,
  not the 2xx; one probe per invalid-input rule; authn and authz; a CLI's
  exit code with stdout and stderr separately; timeouts, retries, idempotency,
  concurrency and partial-failure recovery.
- **docs** (from `/document-release`) — factual items the change made stale
  (paths, commands, flags, counts, tables) are updated in place; narrative,
  positioning, CHANGELOG voice and VERSION are left alone.

## Routing table — what the audit touched → what to recommend

The `/review` line comes first with every matching force flag; at most ONE
extra line follows.

| The audited change touched | Advisory addition |
|---|---|
| Auth, secrets, user input, subprocess, network-facing code | `--security` on the /review line; `/cso --diff` as the extra line |
| Money, quota, gate or approval logic | `--security --testing` on the /review line |
| LLM calls, prompts, tool definitions, MCP, agent loops | `--security` on the /review line; `/cso --code` or `--skills` as the extra line |
| DB schema, migrations, backfills | `--data-migration` on the /review line (add `--performance` for indexes or large tables) |
| Public API surface, webhooks, response shapes | `--api-contract` on the /review line |
| State machines, status enums, workflow transitions | `--state-machines` on the /review line |
| UI components, pages, styling | `--design` on the /review line; `/design-review --build <preview url>` as the extra line |
| Observable behavior: web flow, API, CLI, job, webhook | `/qa-only` as the extra line |
| CLI, tooling, scripts, install flows, SDKs | `/devex-review` as the extra line |
| A refactor, new abstraction, or dependency the audit kept | `--simplification --maintainability` on the /review line |
| Duplicated logic the audit saw outside the footprint | `/deslop-shared-libs` as the extra line |
| Swift / SwiftUI / Xcode targets | `/ios-qa` as the extra line |
| An LLM model choice or a paid eval | `/benchmark-models` or `/eval-plan` as the extra line |
| A perf target the plan named | `/benchmark` as the extra line |
| CI/CD, release pipelines, Docker/IaC, deploy config | `/cso --supply-chain` or `--infra` as the extra line |
| Documented behavior the audit could not update factually | `/document-release` as the extra line (human-run) |
| Change under 50 lines but risk-bearing | The matching force flag(s): without them /review dispatches only `state-machines` |
| Clean and ready to land | `/ship` as the extra line (human-run) |

## Audit-time awareness (facts that change how Step 4 behaves)

- **The post-sweep verification is the citable green.** Evidence binds to
  tree content at both ends: it must come after the LAST edit. Anything
  edited afterwards is exactly what `/ship` and `/land-and-deploy` reject.
- **The repo may declare its verify command.** Phase 4 and the post-sweep
  re-verification both run it. An armed `gstack-verify-gate` holds the turn
  open until it passes: it is a gate, not a harness bug.
- **Residual risks need evidence.** "Unreachable" or "can't" is stated only
  with the verbatim probe output next to it.
- **Accepted shortcuts leave a trail.** The zero-comment sweep keeps a
  `gstack-shortcut(dec-<id>)` marker only when the plan's Decisions to record
  called for it, and never invents one.
- **UI is measured against `DESIGN.md`** tokens, type scale, spacing and
  motion rules; a value present there is never a finding.
- **Guardrails fail closed** and a `/freeze` boundary persists across
  sessions. A fix denied by one is reported and lands in Residual risks.
- **Secrets never reach gstack's memory**; this skill writes neither
  learnings nor timeline.
